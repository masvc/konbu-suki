### インデックスされていなかった原因を特定して直した（canonical が全ページでトップを指していた）

Search Console が36/36ページ未検出のままだったので、配信されている HTML を直接見た。
**全ページの canonical がトップページを指していた。**

```
/guide/kombu-nutrition  canonical: https://konbu-suki.com
/category/dashi         canonical: https://konbu-suki.com
/origin/rishiri         canonical: https://konbu-suki.com
```

`src/app/layout.tsx` の `alternates: { canonical: "/" }` を全ページが継承していた。
検索側には「この記事はトップページの複製です」と伝わる。記事をいくら書いても
インデックスされない。記事の質でも量でもなく、これが原因。

**title も二重になっていた。** layout の `title.template` が `%s | サイト名` で、
各ページは page-meta.ts ですでにサイト名まで含めた title を作っていたため、
「… | コンブスキー | コンブスキー」と配信されていた。

直し方。canonical は layout から外し、`page-meta.ts` が title・description と一緒に
組み立てるようにした。各ページで個別に書く形にすると、書き忘れたページが親の値を
継承して同じことが起きる。固定ページには個別に指定し、トップにも明示した。
title は layout の template をやめ、page-meta の文字列をそのまま使う。

**なぜ点検で気付けなかったか。** `meta-check.ts` は `page-meta.ts` が返す文字列を
検査している。canonical も title の二重付与も layout 側で起きるので、検査対象の
文字列には現れない。page-meta.ts の冒頭に「別々に組み立てると点検側が実際と違う
文字列を検査してしまう」と書いてあったが、layout からの継承と template までは
想定していなかった。

`site-check.ts` に、**配信された HTML を取得して canonical と title を実測する**
検査を足した。page-meta の文字列ではなく、実際に返る HTML を見る。
未デプロイの状態で実行して、上記2件をどちらも検知することを確認した。

### meta description を生成して14本を差し替えた（+ OGP画像・参考文献・Recipe）

`scripts/generate-meta.ts` を追加し、Gemini で説明文を作って差し替えた。

**全記事を置き換えてはいない。** 実測すると20本中17本が100字未満（61〜98字）で、
検索結果の説明文に使える場所を余らせていた。一方、98字ある手書き文に対する案は
104字で、良くなった分がほとんど無かった。そこで **元が100字以上のものは据え置き**
という条件を足し、14本だけ差し替えた（61→139字、72→113字など）。

生成と反映は分けてある。1回の実行で生成してそのまま書き込む形だと、目を通した案と
実際に入る案が別物になる（生成のたびに文面が変わる）。案を JSON に残し、`--apply`
で反映する。

検査で落ちたものがある。これは仕組みが効いた側。

- 「解消」という使えない表現（CLAUDE.md のコンテンツルール）
- `**違い**` という Markdown の記法。そのまま検索結果に出てしまう
- 「もったいない！」「ご紹介します」のような宣伝調。記事本文と声が変わる
- 記事に無い数字・カタカナ語（作文で足されるのを防ぐ検査）

1件だけ目視で確かめた。サーモンの案に「アニサキス対策に酢や塩は効果がありません」
とあり、食品安全の記述なので記事を確認した。厚生労働省を出典として記事に書かれて
いたので、そのまま通した。

あわせて入れたもの。

- **OGP画像**（1200x630）を全20本。元はアイキャッチを使う。生成し直すと、記事の絵と
  SNSに出る絵が別々になり、画像生成の呼び出しも2倍になる
- **参考文献と更新日**を全記事に表示。参考文献は本文の「出典:」行から集める。
  記事ごとに一覧を別に持つと、本文を直したときに片方だけ古くなる
- **Recipe の構造化データ**を、材料と手順がページに見えている2本（だしの取り方・
  昆布水）に付けた。昆布締めの個別記事は分量を本文に書いていないので付けない


### 記事をまたいだ事実の監査を仕組みにした（＋検出した2件を修正）

`scripts/fact-audit.ts` を追加。定期点検（`health-report.ts`）と夜間の新規枠・点検枠に
組み込んだので、記事を足すたびに走る。

見るのは3つ。

1. 複数の記事に書くことになった事実で、記事によって数字が違っていないか
2. 出典の記載が1つも無い記事
3. 古い版を引いていないか（食事摂取基準・食品標準成分表）

全文から数値を拾って突き合わせる形にはしていない。関係のない数字どうしが当たって
誤検知だらけになり、見なくなるため。「複数の記事に書くことになった事実」だけを
RULES に並べる。新しい事実を2本目の記事に書いた時点でルールを足す。

**初回の実行で2件出た。両方直した。**

- 北海道産の割合が `kombu-types` で「約90%」、`kombu-production` で「約95%」。
  北海道 水産林務部が「本道では日本で食べられている昆布の9割を生産しています」と
  明記しているので、95%が誤り。`kombu-production` を書き直した
- `shiokombu-guide` に出典が1つも無かった。社名3つを出典なしで挙げていたので削除し、
  協会の加工品一覧・成分表（塩昆布09022）・ぎょれんの用途記載をもとに書き直した

`kombu-production` には、北海道の資料にある「令和6年には統計を取り始めて以来、
初めて1万トンを下回ることが見込まれた」を入れた。産地の記事で「どこで採れるか」
しか書かないと、採れる量が減っている事実が落ちる。競合が書いていない要素でもある。

`shiokombu-guide` には食材別の組み合わせ表を入れた。topic-map 柱6の「塩昆布の使い方」
はこの記事に吸収する。別記事にすると「塩昆布」で検索意図が被るため。
