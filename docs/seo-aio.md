## AIO（AI検索に引用される）

調べて分かったことと、このサイトの状態。

| 言われていること | このサイトの状態 |
| --- | --- |
| 結論を見出しの直下に置く（BLUF） | **できている。** 全記事が「結論:」の節から始まる |
| 比較・仕様・価格は HTML の表にする | **できている。** 本文に Markdown の表を書かず `GuideSection.table` で本物の table 要素を出す |
| FAQ を3問以上置き、FAQPage の構造化データを付ける | **できている。** 全記事に FAQ と FAQPage |
| 指示語（これ・それ・上記）を使わない | **一部できていない。** 前を指すもの（上記・上の表）は解消したが、「下の表」が9箇所残る。`fact-audit.ts` が検査する |
| E-E-A-T を厚くする | **できている。** 編集方針・データと出典・運営体制・参考文献・訂正の記録 |
| 自然検索で上位を取ることが前提 | **できていない。** そもそもインデックスされていない |

**最後の1行が効いている。** AI検索の引用は、検索で見つかることが前提になる。
いまのサイトは入口が塞がっていたので、AIO の施策だけ積んでも引用されない。

## llms.txt

**Google 検索は llms.txt を使わない。** Google 検索セントラルが公式に、置いても
可視性や順位は上がりも下がりもしないと明記している。約30万ドメインの実測でも
AI引用との相関は見られていない。

このサイトは `/llms.txt` を配信している（2026-11-06 設置）。**Google 向けの効果は
期待しない。** ChatGPT・Claude・Perplexity などが llms.txt をどう扱うかは Google の
管轄外で、こちらは分かっていない。記事一覧から自動で組み立てているので維持の手間は
かからず、外す理由も無いので置いたままにする。**効果があると見込んで施策を積まない。**

## 重さ（Core Web Vitals）

2026-11-07 の実測。

| ページ | HTML | 応答 |
| --- | ---: | ---: |
| トップ | 180KB | 0.10〜0.15秒（ISR再生成時のみ5.9秒） |
| 記事（栄養） | 125KB | 0.17秒 |
| 記事（昆布締め） | 103KB | 0.19秒 |
| カテゴリ（だし） | 317KB | 0.35秒 |
| ガイド一覧 | 39KB | 0.14秒 |

いまは問題にならない水準。重くなるとしたら商品一覧で、カテゴリページが
商品数に比例して伸びる。`site-check.ts` がページ重量を見ている。

守ること。

- **画像は 1200x630 以下・200KB以下**（`optimize-guide-images.ts` が検査する）。
  アイキャッチと OGP は同じ元画像から作る。別々に生成すると枚数も呼び出しも倍になる
- **`"use client"` をページ単位で付けない。** 1つの操作のために付けると、そのページ全体が
  クライアントに送られる。いまは `FaqAccordion` など部品だけに付いている
- 商品一覧は件数に比例して重くなる。カテゴリページが500KBを超えたら件数を絞る

## やらないこと

- **根拠の無い順位付け。** ランキングページは、順位を付けられるデータが揃うまで作らない
  （rating 41/315件、reviewCount 0件、weight 0件）
- **出典の無い数値。** 出典に書かれていない数字は、AIO に効きそうでも書かない
- **メーカーの解説コラムを出典にすること。** 詳細は topic-map「出典に使わない資料」

## 計測

- `npm run facts` — 記事をまたいだ事実の食い違い・指示語・出典ゼロ・古い版
- `npm run ai:citation` — AI検索で引用されているか
- `npm run lighthouse` — Core Web Vitals（`PAGESPEED_API_KEY` が要る）
- `npm run check` — サイト品質・リンク・meta・構造化データ・canonical
